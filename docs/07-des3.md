# 07 — DES3-EDE pipeline

The cipher stage runs **three identical passes** of 3DES-EDE
decryption with permissive unpad after each. This is **not** a
cryptographic standard; it's a composition of a standard primitive
and a non-standard unpad.

## Pass formula

```text
F(X) = D_K1( E_K2( D_K3( X ) ) )        # standard 3DES-EDE, decryption direction
                                        # ECB, 8-byte block

pt_1 = unpad( F(ciphertext) )
pt_2 = unpad( F(pt_1) )
pt_3 = unpad( F(pt_2) )                 # the printed candidate
```

**Permissive unpad**:

```python
def unpad(x):
    if not x:
        return x
    n = x[-1]
    if 1 <= n <= 8 and n <= len(x):
        return x[:-n]
    return x
```

Not PKCS#5: no multi-byte consistency check, no reject on invalid.

## Key assembly

```python
f = f_user(username)                           # user-VM, byte-exact replica
r = RC4(key=b'\0').encrypt(serial)             # serial-VM, byte-exact replica
key = (f + r)[:24].ljust(24, b'\0')            # 24 bytes, zero-padded as needed

K1 = key[0:8]
K2 = key[8:16]
K3 = key[16:24]
```

The DES PC-1 drops the LSB of every key byte. Byte 0 of the key, byte
8, byte 16 all contribute 7 bits of entropy each (not 8).

## Replica

[`src/pafet_des3_xxi.h`](../src/pafet_des3_xxi.h) is ~230 LOC of pure
C++ DES + 3DES-EDE + permissive unpad. Full FIPS 46-3 tables (IP, FP,
E, P, PC-1, PC-2, ROT, 8 S-boxes).

Public interface:

```cpp
namespace pafet_des3_xxi {
    // Returns the 3-pass decrypt result after unpadding, or empty on
    // partial-block guard (bytes_in % 8 != 0 after unpad).
    std::vector<uint8_t> decrypt_material(const uint8_t ct[72], const uint8_t key[24]);
}
```

## Why permissive unpad matters

Permissive unpad means the plaintext length after each pass is
whatever happens to be in the last byte of the DES block, modulo the
range `[1..8]`. Two consequences:

1. **Non-PKCS#5 inputs decrypt to variable-length output.** A pass
   whose last block ends in `0x02 ??` (with the second byte not
   `0x02`) would be rejected by PKCS#5 but accepted here with a
   2-byte strip.
2. **Flag length is data-dependent.** For a correct `CMO{...}` flag,
   the three unpads land on bytes that strip `len(ct) - len(flag)`
   bytes total across the three passes.

The three-pass structure is **not** standard 3DES. Standard 3DES
applies the EDE cipher once with a 24-byte key; here the author
applies the full EDE three times with the same key, interleaved with
unpads. This gives the author a way to force the flag through three
different `len % 8` reductions before it is tested.

## Oracle at the ciphertext level

For `ramon / barcelona` keyed against the recompiled Pafet (which uses
the ciphertext computed from the plaintext
`CMO{pafet_rekeyed_by_ramon______...}`), the key is:

```text
key = f_user("ramon") ++ g_serial("barcelona") ++ pad
    = 3b 3f 44 4b 3b  ++  7f ae 76 a5 bb ...  ++  00 ...
```

The ciphertext is 72 bytes. After 3 passes of F + unpad, we get back
the plaintext `CMO{pafet_rekeyed_by_ramon______...}` byte-for-byte.
See `src/pafet_recompile_xxi.cpp` and `src/build_recompile_xxi.bat`.

## Why no shortcut (meet-in-the-middle, slide, etc.)

Early audit (`PAFET_CRYPTO_AUDIT.md`) considered:

- **2-anchor MITM at 8+8**: works on synthetic examples under one
  specific nested padding; a synthetic counterexample proves ciphertext
  size + flag shape do NOT imply that padding. Table cost is ~2^56
  entries (~1.5 EiB for 24-B records) without bounded candidate sets.
- **Partial last block**: reads past the string's logical length. Its
  tail depends on memory slack. First 8 plaintext bytes are
  independently computable; the rest aren't without the full key.
- **Related-key**: the key is a function of the username and serial;
  attempting related-key attacks requires an oracle, which we don't
  have (gate blocks all attempts).

Final honest statement: without a SHA-256 preimage for the gate hash,
there is no practical path to the real flag. The crypto is correctly
reconstructed; the preimage is the actual secret.
